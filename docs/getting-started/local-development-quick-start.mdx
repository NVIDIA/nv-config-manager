Use this guide when you want to bring up the local development environment to preview Config Manager functionality without a real lab. The local environment is useful for previewing rendered configurations, exploring the Config Manager UI, browsing Config Store output, validating DHCP reservations and ZTP provisioning chains, and exercising Temporal workflows end-to-end against mock network device pods.

## What this gives you

There are two local deployment modes depending on what you want to test.

Both modes deploy the same superpod mock topology. Use the generated topology as a reference for the kinds of objects your own site data needs: locations, devices, roles, platforms, interfaces, prefixes, IP addresses, cables, VLANs, VRFs, tenants, config contexts, and managed-device metadata.

The sample data is loaded by a Nautobot Design Builder job. See [Design Builder Data Loading](../nautobot/design-builder-data-loading.mdx) for the job structure and for guidance on replacing the sample topology context with your own data.

<Warning title="Mock topology data is not production data">
The bundled mock topology data must never be used for a real deployment.
</Warning>

### `make kind-up` — render and UI preview

Deploys Config Manager with an in-cluster Nautobot, sample site data, generated secrets, and no SSO. Workflows are routed through a hardcoded `MockNetworkConnection` stub, which means workflow code paths execute but no real device API is called. Use this for fast inner-loop development: rendering configs, navigating the UI, browsing Config Store output, and modeling Nautobot data shapes.

### `make sandbox-up` — full mock device sandbox

Deploys Config Manager with `mock_devices: false`, builds and loads mock device API pods (FastAPI servers emulating Cumulus NVUE and Arista EAPI), and wires their Kubernetes ClusterIPs into Nautobot as `primary_ip4`. Temporal workflows reach the mock pods over real `NetworkConnection` code paths.

This mode is useful for:

- Testing DHCP reservation generation and ZTP provisioning chains end-to-end
- Running backup and cable validation Temporal workflows against mock devices
- Exercising `CumulusConnection` / `AristaConnection` code without physical hardware

<Warning title="Partial workflow coverage">
The mock device pods cover backup, cable validation, DHCP, and ZTP. Workflows that mutate device state — deploy, multi-deploy, reprovision, password rotation, and hardware validation — execute against the mock API but produce simplified or stub responses and are not a substitute for testing against real hardware.
</Warning>

See `development/mock_devices/README.md` for full documentation on the mock device CLI, fixture system, and all available make targets.

## Prerequisites

- Docker
- Kind
- Helm 3.x
- `kubectl`
- Python 3.11+
- `uv`
- At least 8 vCPU, 24 GB RAM, and 30 GB free in Docker storage for the small local profile

Use the standard local Kind cluster name so image loading targets the right cluster:

```bash
kind create cluster --name nv-config-manager --config deploy/kind-config.yaml --wait 5m
```

## Deploy a local development preview

### Render and UI preview (fast)

```bash
make kind-up
```

Equivalent headless installer command:

```bash
cd installer
uv run nvcm-installer deploy ../deploy/configs/local-superpod.yaml \
  --image-source local \
  --build-images \
  --load-kind \
  --kind-cluster nv-config-manager \
  --install-envoy-gateway \
  --install-cnpg-operator \
  --install-cert-manager
```

After `kind-up` completes:

1. In Nautobot, inspect the generated site, devices, interfaces, cables, prefixes, and config contexts.
1. In the Config Manager UI, inspect workflow forms and existing config links.
1. In Config Store, confirm intended configs exist for generated devices.
1. Edit a safe Nautobot object that affects render output and confirm the intended config updates.

### Full mock device sandbox

```bash
make sandbox-up
```

This runs `kind-up` with the superpod topology, then builds the mock device image, deploys mock device pods, and wires their ClusterIPs into Nautobot automatically. Allow an extra ~5 minutes for the mock device image build and wiring job.

After `sandbox-up` completes:

1. Run `make mock-dhcp-validate` to confirm a DHCP reservation exists for the device named by `MOCK_DHCP_DEVICE` (default `a04-u44-p01-tor-01`; override with `make mock-dhcp-validate MOCK_DHCP_DEVICE=<name>`).
1. Run `make mock-ztp-validate` to walk the ZTP provisioning chain for the device named by `MOCK_ZTP_DEVICE` (default `a04-u44-p01-tor-01`; override with `make mock-ztp-validate MOCK_ZTP_DEVICE=<name>`).
1. Run `make mock-workflow-backup` to start the Temporal backup workflow, then check the Temporal UI at `https://temporal.config-manager.local` to confirm the workflow completes.

## Access the local services

Add local hostnames for the Envoy Gateway.

```text
127.0.0.1 config-manager.local
127.0.0.1 nautobot.config-manager.local
127.0.0.1 render.config-manager.local
127.0.0.1 ztp.config-manager.local
127.0.0.1 dhcp.config-manager.local
127.0.0.1 workflow.config-manager.local
127.0.0.1 config-store.config-manager.local
127.0.0.1 temporal.config-manager.local
127.0.0.1 mcp.config-manager.local
```

Then open:

| Service | URL |
| :------ | :-- |
| Config Manager UI | `https://config-manager.local` |
| Nautobot | `https://nautobot.config-manager.local` |
| Workflow API | `https://workflow.config-manager.local` |
| Config Store API | `https://config-store.config-manager.local` |
| MCP endpoint | `https://mcp.config-manager.local/mcp` |

For the local profile, Nautobot login is `admin` / `admin`.
